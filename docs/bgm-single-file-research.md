# 단일 OGG 동기화 우회 조사 — 2026-09-22

## 결론

**이미 접속한 플레이어에게 곡 시작부터 멀리 있는 음원으로 미리 재생해 놓고, 필요할 때 가까이 이동시키는 방식은 오디오 계층에서 동작했다.** 원본 전체 OGG 한 개를 사용하며 재생을 다시 시작하지 않는다. 그러나 새로 접속한 플레이어에게 과거 재생 위치를 복사하는 기능은 아니다. 현재 로비 → 전장의 월드 변경, 클라이언트 스트리밍 채널 수, 모노 변환 등 별도 제약이 있어 곧바로 실서비스에 적용하지 않았다.

서버는 곡 ID와 시작 시각을 복사할 수 있지만, 실제 Vorbis 디코더·OpenAL 소스·PCM 큐는 각 클라이언트 프로세스 안에 있다. 기존 클라이언트의 오디오 재생 상태를 새 클라이언트에 전송하고 복원하는 바닐라 패킷은 확인되지 않았다. 같은 Sound 패킷을 새 플레이어에게 보내면 새 소리를 처음부터 생성한다.

## 실제 실험

공식 Minecraft Java 1.21.8 client JAR의 **원래 Channel 및 JOrbisAudioStream 클래스**를 수정하지 않고 사용했다. OpenAL Soft loopback 장치로 오디오를 메모리에 렌더링했으며 실제 스피커 출력이나 Minecraft 서버 접속은 하지 않았다. 리플렉션은 실험 프로그램에서 원래 클라이언트 클래스를 호출하기 위한 것으로, 서버가 원격 플레이어의 오디오 엔진을 조작했다는 뜻이 아니다.

8초짜리 전체 OGG를 한 번 재생하고, 소스 위치를 128블록 거리로 두어 3초 렌더링한 뒤 원점으로 이동했다.

| 결과 | 모노 | 스테레오 대조군 |
|---|---:|---:|
| 멀리 있을 때 출력 RMS | 0 | 0.126294448 |
| 가까이 이동 후 출력 RMS | 0.106118254 | 0.125708266 |
| 위치 이동 전/후 큐 내 재생 오프셋 | 0.982667 / 0.982667초 | 동일 |
| 재생 시작 호출 수 | 1 | 1 |

오프셋은 OpenAL의 현재 스트리밍 큐 기준이며 곡 전체의 절대 시각이 아니다. 이미 3초를 렌더링했고, 위치만 바꾼 순간 이 값이 바뀌지 않았다는 점을 검사했다. 모노는 그동안 무음이었지만 계속 재생되었고, 다시 시작하지 않고 가청 상태가 되었다. 스테레오는 원래 거리 감쇠가 적용되지 않아 이 방식으로 숨길 수 없었다.

[원본 결과 JSON](audio-research/silent-playback-result.json)

추가로 `LOOPSTART=144000`, `START=3`, `offset=3`, `start_offset=3` 태그를 넣은 OGG를 Minecraft의 원래 디코더에 전달했다. 첫 1초의 PCM SHA-256은 원본과 동일한 `5673a494e585aa3520856167995e8eee9c135a95a6823800af1712cde8616bde`였다. 중간 OGG 페이지 7개의 granule position을 3초만큼 바꾸고 CRC를 다시 계산한 별도 실험도 첫 PCM이 동일했다. 이 조작들은 3초 위치로 seek하지 않았다. 모든 가능한 비표준 OGG 변형을 배제하는 증명은 아니다.

## 클라이언트 코드에서 확인한 제약

- `sounds.json` 파서에는 시작 시각·seek 필드가 없다. `SoundBufferLibrary`는 리소스를 InputStream으로 열고 새 디코더를 만든다.
- 일반 사운드 pitch는 SoundEngine에서 0.5–2.0으로 제한된다. 큰 pitch 값으로 순간적으로 빨리 감는 방식은 성립하지 않는다.
- 일반 RECORDS 소리를 volume=0으로 시작하면 SoundEngine이 재생 자체를 건너뛸 수 있다. 선재생 후보는 양수 볼륨과 거리 감쇠를 사용한다.
- `EntityBoundSoundInstance`는 매 틱 엔티티 위치를 따라가므로, 개인별 가상 음원을 이동시키는 후보가 된다. 실제 엔티티 패킷을 통한 전체 클라이언트 검증은 아직 하지 않았다.
- 1.21.8의 Library는 스트리밍 채널 수를 2–8로 제한한다. 모든 활성 세션의 곡을 모든 플레이어에게 미리 틀어 놓는 방식은 확장성이 좋지 않다.
- `Minecraft.setLevel()` → `updateScreenAndTick()`에서 SoundManager.stop()이 호출된다. 현재 프로젝트는 `mud_lobby`와 `moma_arenas`를 나누고 관전 시작 시 텔레포트하므로, 로비에서의 선재생을 그대로 유지하는 방식에는 월드 전환 문제가 있다.
- 서버 구동기나 Rust 연산 모듈을 바꾸어도 클라이언트에 없는 seek 명령이나 재생 상태 복원 기능이 생기지는 않는다.

## 후보 비교

| 방법 | 음원 분할 | 임의 시점의 신규 접속자 | 판단 |
|---|---|---|---|
| 음원·타임라인 정보만 복사 | 없음 | 해당 위치 적용 불가 | 정보 전달과 클라이언트 재생 위치 적용은 별개 |
| 동일 패킷·seed 재전송 | 없음 | 처음부터 재생 | seek 대체 불가 |
| 거리 감쇠로 미리 재생 | 없음, 모노 필요 | 곡 시작부터 준비되지 않았다면 불가 | 제한적 후보, 오디오 계층 실험 성공 |
| 원본 1개 + 필요할 때 남은 구간 OGG 1개 생성 | 짧은 조각을 미리 수백 개 만들지는 않음 | 준비·다운로드 후 미래 시점에 합류 가능 | 별도 잔여 음원이므로 엄밀한 원본 그대로 seek는 아님 |
| 클라이언트 모드 또는 브라우저 | 없음 | 가능 | 사용자 설치/브라우저 요구사항 변경 |

신규 접속자까지 지원하는 무모드 우회 후보는, 서버에 원본 한 개를 보관하고 **미래 합류 시점부터 끝까지 이어지는 OGG 한 개만 필요할 때 만드는 방식**이다. 예를 들어 현재 43초라면 준비 시간까지 고려해 55초부터의 음원을 만들고, 리소스팩 적용 완료를 확인한 뒤 55초 시점에 한 번 재생한다. 늦게 준비되면 다음 시점을 다시 선택하거나 다음 곡을 기다려야 한다. 기존처럼 2초마다 교체하지 않지만, 추가 다운로드와 일회성 지연이 있으며 아직 구현·검증하지 않은 설계다.

## 재현 및 출처

프로브는 `benchmarks/audio-research`에 있으며 `scripts/run_audio_research.ps1`로 실행한다. 설치된 1.21.8 라이브러리, 원본 client JAR, ffmpeg가 필요하다. Minecraft 파일이나 라이브러리는 저장소에 포함하지 않는다.

```powershell
./scripts/run_audio_research.ps1 -ClientJar <1.21.8-client.jar> -Ffmpeg <ffmpeg.exe>
```

실험 client JAR SHA-256: `ea74e9c5e92d01f95f3d39196ddb734e19a077a58b4c433c34109487d600276f`.

- 공식 런처의 1.21.8 버전 메타데이터가 지정한 Mojang client JAR 및 공식 매핑을 분석했다.
- [OpenAL 사양 및 속성 정의](https://raw.githubusercontent.com/kcat/openal-soft/master/include/AL/al.h): 거리 감쇠, 재생 소스와 위치·오프셋은 서로 다른 속성.
- [NeoForge 음원 문서](https://docs.neoforged.net/docs/resources/client/sounds/): 모노·스테레오 거리 감쇠 차이.
- [Paper 실제 사운드 패킷 생성 코드](https://github.com/PaperMC/Paper/blob/main/paper-server/src/main/java/org/bukkit/craftbukkit/entity/CraftPlayer.java): 전송되는 사운드 인자 확인.
- [OpenAudioMc 재생 옵션](https://docs.openaudiomc.net/docs/play_command), [브라우저 클라이언트](https://docs.openaudiomc.net/docs/client_guide): 시작 위치와 중간 합류를 지원하지만 별도 웹 플레이어를 사용.

위 단일 파일 우회 방식은 조사·실험만 수행했으며 운영 서버나 현재 BGM 구현에 적용하지 않았다. 최종 채택한 제품 방식은 전체곡과 분할곡을 함께 두고 곡 경계에서 전환하는 방식이다.
