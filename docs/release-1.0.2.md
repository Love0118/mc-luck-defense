# 1.0.2 — 자동 배치 계산 분산

## 변경

- 자동 배치의 최적 위치 계산을 두 작업 스레드에서 수행한다. 서버 스레드는 포탑의 ID·종·등급·전투 수치·현재 위치를 복사하고, 작업 스레드는 이 복사본만 읽는다.
- 세션마다 계산은 한 개만 진행한다. 실제 서버 틱마다 완료된 결과를 반영하고, 필요한 다음 계산을 예약한다. 결과가 아직 없으면 기존 배치로 전투를 계속한다.
- 계산 도중 소환·합성·판매·수동 이동으로 입력이 달라지면 결과를 버리고 다시 계산한다. 실제 엔티티 이동과 게임 상태 변경은 서버 스레드에서만 수행한다.
- 세션 종료와 런타임 교체 시 남은 계산을 취소한다. 계산 대기열이 가득 차면 다음 틱에 다시 시도하며 게임 스레드에서 기다리지 않는다.
- 일괄구매는 기존처럼 시뮬레이션 틱당 최대 4회다. 뽑기 확률·가격·배속별 구매량·전투 수치·파티클 수와 표현은 그대로다. 배치 반영 시점은 계산 완료 후 서버 틱이며, 동점인 위치는 반영 시점에 따라 달라질 수 있다.

## 적용

런타임 상태 형식은 4를 유지한다. `/mud update check`로 확인한 뒤 `/mud update`로 적용한다. 1.0.0·1.0.1과 호스트 및 밸런스 지문이 같아 진행 중인 세션을 유지할 수 있다. 계산 작업은 저장 상태에 포함하지 않으며 교체된 런타임이 필요한 배치를 다시 계산한다.

운영 서버에서는 Paper의 CPU 제한을 한 코어에서 0·1·2번 코어로 확장했다. 실행 중인 Netty 스레드에도 즉시 반영해 ViaVersion·ViaBackwards의 접속별 패킷 변환이 여러 코어에서 실행되는 것을 확인했다. 한 접속자의 패킷은 같은 이벤트 루프에서 순서대로 처리되므로 접속 하나의 변환 작업을 여러 코어로 나누지는 않는다. 이 설정은 서버 운영 설정이며 플러그인 업데이트만으로 다른 서버의 CPU 제한까지 바뀌지는 않는다.

Java 시작 옵션의 `ActiveProcessorCount`도 3으로 맞췄다. 이 JVM 인식값은 다음 정상 재시작부터 적용된다. 실행 중인 서버의 OS 스레드 제한은 이미 해제했으며, 진행 중인 게임을 위해 재시작하지 않았다.

## 검증

기존 자동 배치·자동 구매·세션 배속 테스트를 수정해 계산 완료 전 상태 보존, 판매 후 오래된 결과 폐기, 자동 배치 해제 후 수동 위치 보존, 1배와 32배의 구매량·승급·소환 단계 일치를 확인한다. 동점인 좌표의 완전 일치 대신 각 결과가 기존 배치 알고리즘의 최적 배치를 만족하는지 확인한다. 새 테스트 파일이나 테스트 항목은 추가하지 않았다.

`mvn -B -ntp verify` 결과 기존 350개 테스트가 모두 통과했다.

실서버 JFR에서 ViaVersion·ViaBackwards의 파티클 변환이 CPU를 많이 쓰는 것을 확인했다. CPU 제한 변경 뒤 Netty 스레드가 서로 다른 코어에서 실행되는 것도 확인했다. 두 측정 시점의 게임 부하가 달라 성능 개선율로 비교하지 않는다.
