# 1.0.20 → 1.0.22 진행 중 세션 업데이트 검증

앞선 검증은 로컬 자동 검사와 1.0.21 배포 JAR의 호환성 비교였다. 추가로 **실제 Paper 26.3 테스트 서버에서 게임을 진행하며 1.0.20 → 1.0.22를 교체**했다.

1.0.20은 `e0e2d6629af95b5beca6941b187ea3ad3e4d4d10`, 1.0.22는 `cf1c817c8920741f664ea6df9b0dda3bee19c824`의 GitHub 배포 JAR를 사용했다. 로더·저장 형식·밸런스 해시가 모두 같다. 테스트 서버는 127.0.0.1:25585에서만 열었고, 1.21.8 프로토콜 클라이언트 3개를 ViaVersion/ViaBackwards로 접속시켰다. 라이브 서버를 리로드하거나 재시작하지 않았다.

## 진행 중 상태

배치 기물 36개·대기 기물 4개, 살아 있는 적, 선택한 기물, 골드, 4배속 게임, 관전자, 기존 소환 알림 OFF 상태를 준비했다. 준비 시간이 끝나 1라운드가 실제로 시작된 뒤 다운로드 업데이트의 일반 적용 경로 `installDownloaded(path)`를 실행했다. `force`는 사용하지 않았다.

교체 직전과 직후 게임 상태 전체의 fingerprint가 정확히 일치했다. 이 비교는 라운드·시간·재화·기물·강화·선택·배치·대기열·전투 대기시간·난수 진행 상태·관전 정보를 포함한다. 세션 UUID와 관전 대상, 모든 기물·적 엔티티 UUID, 플레이어·관전자 위치, 비행 상태, 관전자의 모험 모드와 투명 상태를 유지했다. 이전 GUI는 닫혔고 새 런타임에서 게임이 계속 진행됐다. 교체 후 게임 루프가 중복되지 않는 것도 확인했다.

## 환경설정·수신 결과

로비를 활성화한 상태에서 게임 참가자·관전자·로비 이용자 모두 6번 칸 아이템이 비교기로 갱신됐다. 우클릭 Bukkit 이벤트로 실제 등록된 리스너를 통해 환경설정 GUI를 열었으며, 각 클라이언트가 새 창 패킷을 수신했다. GUI 클릭 이벤트로 ON/OFF를 변경하고, 같은 틱의 중복 클릭이 한 번만 적용되는 것을 확인했다.

| 조건 | 참가자 소환 방송/소리 | 관전자 소환 방송/소리 | 로비 이용자 소환 방송/소리 |
|---|---:|---:|---:|
| 내 소환 OFF·관전자 다른 소환 OFF | 0 / 0 | 0 / 0 | 1 / 1 |
| 내 소환 ON·관전자 다른 소환 ON | 1 / 1 | 1 / 1 | 1 / 1 |

참가자의 다른 소환은 OFF인 상태에서도 자기 소환 ON이 독립적으로 적용됐다. 라운드 알림 OFF 동안 게임은 두 라운드 이상 진행됐고 클라이언트가 받은 라운드 채팅은 0개였다. GUI에서 다시 ON으로 바꾸면 다음 라운드 채팅 1개를 받았다.

GUI 입력은 테스트 플러그인이 Bukkit 이벤트로 발생시켰고, 화면·알림·소리는 실제 접속 클라이언트의 패킷으로 확인했다. 사람의 마우스 조작이나 렌더링된 화면을 확인한 테스트는 아니다. 실제 `/mud update`의 GitHub 다운로드 요청 자체는 이 테스트에서 다시 실행하지 않았고, 검증된 배포 파일을 동일한 일반 적용 함수에 전달했다.

초기 테스트 환경에서 기본 화이트리스트, 복사한 전장의 등록 누락, 비활성화된 로비 때문에 검증이 중단된 시도가 있었다. 이를 수정하고 로비가 활성화된 새 테스트 디렉터리에서 전체 검사를 통과했다. Windows 시스템 성능 카운터의 시작 경고는 있었으나 플러그인 업데이트 오류는 없었다.
